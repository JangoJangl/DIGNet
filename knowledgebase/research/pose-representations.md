# Pose representations, pose embeddings and generating several poses per pass

Three questions: (1) how do current grasp generators and VLAs represent poses, (2) are poses embedded (learned latents, tokens), (3) does it make sense for DIGNet to produce several poses jointly instead of one pose per sample.

Evidence level: entries marked *(abstract checked)* were re-read on 2026-10-25; the rest is from the papers as remembered and should be re-checked before it is quoted.

## 1. Pose representations in use

### Grasp generators (6-DoF parallel jaw)

| Representation | Used by | Notes |
|---|---|---|
| Translation + quaternion | 6-DOF GraspNet (VAE) and many regressors | Double cover (q = -q) and a discontinuity for a network output. Fine as a storage format, poor as a regression target. |
| Translation + 6D rotation (first two columns, Gram-Schmidt) | Very common regression/diffusion target since Zhou et al. 2019 *(abstract checked)* | Continuous, which is why it is the default for regression. In a diffusion model the noisy 6D vector is off the manifold and has to be projected. |
| Full SE(3) on the group (rotation matrix + translation, Lie algebra for noise/velocity) | SE(3)-DiffusionFields, EquiGraspFlow, DexGraspFlow, GraspMF (see [[research/flow-matching-se3]]) | No representation discontinuity, noise and paths live on the group. DIGNet's flow matching does this. |
| se(3) / pseudo log map vector | DIGNet default (`se3_pseudo_log_map_representation`) | Compact (6D) but wraps at pi, so DDPM on it has a discontinuity (P-15). Flow matching avoids it by only using Log locally. |
| Contact-based: contact point + approach + baseline direction + width, one per point | Contact-GraspNet, AnyGrasp lineage (dense) | Reduces the grasp to geometry on the visible surface, very data efficient, one grasp per point. |
| Learned latent of the grasp | GraspLDM (latent diffusion in a VAE latent) | See section 2. |
| DiT diffusion over grasp poses, sampled grasps scored and filtered by a discriminator | GraspGen *(abstract checked)*, GraspGen-X conditions additionally on a gripper "swept volume" *(abstract checked)* | The abstract does not state the exact parametrisation. |

### VLAs and robot policies

| Representation | Used by | Notes |
|---|---|---|
| 7-D delta end-effector action (dx, dy, dz, droll, dpitch, dyaw, gripper), 256 bins per dimension, bins mapped to LLM tokens | RT-1, RT-2, OpenVLA | Euler deltas are acceptable because deltas are small, no wrap-around. Autoregressive, one token per dimension and step. |
| Discrete tokens of a whole action chunk: DCT over time, quantisation, BPE | FAST / pi0-FAST *(abstract checked)* | Per-dimension binning "typically performs poorly" on high-frequency data. pi0-FAST matches diffusion VLAs and trains up to 5x faster. |
| Continuous action chunks generated by flow matching in an action expert, actions linearly projected to tokens, time added with an MLP | pi0, pi0.5, SmolVLA (LeRobot), GR00T N1 (DiT action head with embodiment-specific encoders/decoders) | The current default in open VLAs. Chunks of about 50 steps. |
| Continuous action chunks decoded in parallel with an L1 loss | OpenVLA-OFT *(abstract checked)* | LIBERO 76.5 % to 97.1 % and 26x throughput versus autoregressive discrete OpenVLA. |
| Actions in a learned, motion-centric local frame (per-step rotation R_t in SO(3) and prototypes) instead of the world frame | MCF-Proto 2026 *(abstract checked)* | More robust to geometric perturbations. Shows that the *frame* of the pose matters as much as the parametrisation. |
| Joint positions (absolute) | ACT, SmolVLA and pi0 on SO-100/SO-101 in LeRobot | Low-cost arms are mostly controlled in joint space. A grasp pose from DIGNet has to go through IK (5-DoF, see [[research/lerobot-so101]]). |

**Conclusion.** Grasp generators converged on continuous SE(3): either 6D rotation for regression or group-valued rotations for diffusion and flow matching. VLAs converged on continuous action chunks with flow matching or L1 heads. Discrete tokens survive where an LLM decodes actions (FAST), and in that case they need compression to be competitive. For DIGNet the current choice is in line with the state of the art: SE(3) flow matching with a 6D network input and a Lie-algebra velocity output.

## 2. Are embeddings used for poses?

There are two meanings, and both are used.

1. **Input embedding of the (noisy) pose.** Every network lifts the low-dimensional pose to its hidden width: a linear layer or MLP (pi0 projects actions linearly), often with Fourier or sinusoidal features. Diffusion and flow models always embed the time step this way. Fourier features on positions help MLPs resolve millimetre detail (NeRF effect). DIGNet does the plain version: an MLP on `[p, rot6d]` plus a sinusoidal time embedding. **Cheap upgrade:** Fourier features of the translation in the object frame, with frequencies matched to object scale (1 mm to 20 cm), and of the 6D rotation entries.
2. **Learned latent or token of the pose.**
   - VAE latents (GraspLDM), so that the diffusion model runs in a learned latent space.
   - VQ codebooks (VQ-BeT, VQ-based VLA heads).
   - Token embedding tables of binned or BPE actions (OpenVLA, FAST).

   These pay off when the action is high-dimensional (long chunks, dexterous hands, several embodiments) or has to share a vocabulary with an LLM. A 6-DoF jaw grasp is only 6 to 9 numbers, and the precision target is millimetres and a few degrees. A learned latent adds a reconstruction error floor and a second training stage, and it saves almost nothing. Tokenising (256 bins over ±10 cm gives 0.8 mm, but rotations need more care) only makes sense if DIGNet is later wrapped into an LLM-based VLA.

**Recommendation:** no learned pose latent and no tokens. Keep the continuous group representation and consider Fourier features on the input ([[state/ideas#I-19 Fourier features for the grasp input]]).

## 3. Several poses per forward pass?

Three different things hide behind "several poses at once".

| Variant | What it is | Status in DIGNet |
|---|---|---|
| A. Batched independent samples | K noise samples, the point cloud is encoded once and the denoiser runs on K queries in one batch | Already implemented (`num_samples`). Computationally this already is "many poses per pass". |
| B. Joint set generation | K grasps are generated *together* and see each other (self-attention between grasp tokens, or set prediction with Hungarian matching) | Not implemented. |
| C. Action chunking | A *temporal* sequence of poses (pre-grasp, grasp, lift) | Not implemented, and not the same thing as B. |

**Evidence for B.**
- DGTR (Dexterous Grasp Transformer) *(abstract checked)* frames grasp generation as set prediction and produces "a diverse set of feasible grasp poses ... with only one forward pass". They need extra training tricks against collapse and implausible poses (dynamic matching, adjustment at test time).
- Group Diffusion *(abstract checked; images, not robots)* denoises a group of samples with shared attention. Larger groups give better quality (up to 32 % FID).
- Dense methods such as Contact-GraspNet are B in its extreme form: one grasp per point. Implicit Grasp Diffusion *(abstract checked)* argues that dense prediction is limited to one grasp per location and combines it with local diffusion sampling.
- GraspGen and most SE(3) diffusion and flow papers stay with A plus a discriminator.

**Why action chunking (C) does not transfer directly.** The elements of a chunk are consecutive and strongly correlated. The elements of a grasp set are alternative modes that should be *different*. OpenVLA-OFT's gains come from temporal consistency and fewer decoding calls, not from better coverage of alternatives. C becomes relevant later for execution on the SO-101: predicting pre-grasp → grasp → lift as a short chunk in joint space would plug into LeRobot policies directly.

**Assessment for DIGNet.**
- Pro B: explicit control of diversity and coverage (samples can avoid duplicates), a natural fit to ACRONYM's ~2000 grasps per object (train on random K-subsets), and possibly fewer samples needed for the same coverage.
- Contra B: a fixed K, a permutation-invariant loss (Hungarian matching or Chamfer on sets) or a set-level diffusion target, harder training, and the risk of collapse onto a few modes. Speed is not a gain, because A already shares the encoder and costs only K denoiser queries.
- A cheap middle ground with good evidence from generative modelling is **minibatch optimal transport coupling** (multisample flow matching, Pooladian et al. 2023; Tong et al. 2023). Per object, match the noise samples to the target grasps with Hungarian or Sinkhorn before computing the flow targets. Paths become straighter, sampling needs fewer Euler steps, and the model and inference stay unchanged (variant A).

**Recommendation.**
1. Keep A as the default.
2. Try OT coupling first ([[state/ideas#I-17 Minibatch OT coupling for flow matching]], S).
3. Run a set denoiser (self-attention between K grasp tokens plus cross-attention to point tokens) only as a controlled experiment ([[state/ideas#I-18 Joint set generation of grasps]], M). Compare coverage and precision at a fixed sample budget (K = 16, 64, 200) against A plus OT coupling.
4. Postpone chunking until the SO-101 execution stage.
